# Green Fire — sistema de gestión

Sitio público y sistema de gestión (ventas, pedidos, stock, caja, compras, producción, facturación) para Green Fire SRL: una fábrica de sustratos y varios locales, cada uno con su propia entidad fiscal.

## Documentos de referencia

- `docs/SegundoIndormePP.pdf`: requerimientos originales.
- `docs/complemento.md`: complemento de requisitos. Si contradice al original, manda el complemento.
- `docs/modelo-datos.dbml`: modelo de datos, **única fuente de verdad**. Cualquier cambio de tablas se hace primero ahí y después en una migración.

## Estructura

- `index.html`, `assets/`, `img/`: sitio público.
- `privado/`: interfaces internas. Hoy usan datos de prueba en `privado/shared/db.js` (modelo viejo, pendiente de conectar a la API).
- `backend/`: API Spring Boot, que además sirve el front como archivos estáticos (solo `/`, `/index.html`, `/assets/**`, `/img/**` y `/privado/**`).

## Backend

- Java 21, Spring Boot 3.4.x, Maven (usar `./mvnw`), PostgreSQL 16 y Flyway.
- Paquete raíz `com.greenfire`, con un subpaquete por módulo: `config`, `comun`, `seguridad`, `ambitos`, `fiscal`, `usuarios`, `auditoria`. Cada módulo contiene sus entidades, repositorios, servicios, controladores y DTOs.
- Código, tablas y endpoints en español, sin tildes ni eñes en los identificadores (`dueno_local`, `ambitos`).

### Base de datos

- Migraciones en `backend/src/main/resources/db/migration`, con el nombre `V<n>__<descripcion>.sql`. Una migración ya aplicada no se modifica: se agrega otra.
- Hibernate solo valida el esquema (`ddl-auto: validate`); las tablas las crea Flyway.
- Ids `bigint generated by default as identity`.
- Todas las tablas del modelo llevan `created_at` y `updated_at` (`timestamptz`, con default `now()`). Las entidades JPA extienden `comun.EntidadBase`.
- Los enums del modelo van como `varchar` con `CHECK`, nunca como tipos enum de PostgreSQL. En Java, las constantes del enum se escriben igual que el valor de la base (`dueno_local`, `responsable_inscripto`), así se mapean con `@Enumerated(STRING)` y la API usa los mismos valores.
- Toda operación auditable se registra con `auditoria.Auditor`. Las ediciones usan `comun.Cambios`, que guarda solo los campos que cambiaron, con su valor anterior y el nuevo.
- La auditoría se guarda en la misma transacción que la operación (`auditoria.RegistroAuditoria`, propagación MANDATORY). Si el insert falla, se revierte todo y la API responde 500. Auditar fuera de una transacción es un error.
- `auditoria.Redactor` reemplaza por `[oculto]` todo campo del detalle cuyo nombre contenga password, contrasena, hash, token, certificado o secret. Al nombrar campos nuevos con datos sensibles, usar esas palabras.
- La tabla `auditorias` es solo de inserción: la base rechaza UPDATE, DELETE y TRUNCATE (migración V2), y `AuditoriaRepository` solo tiene `save`.
- Cada registro guarda el ámbito activo de quien actúa (`ambito_id`) y el ámbito que toca la acción (`ambito_afectado_id`, V3). Toda alta, edición o desactivación que toque a un ámbito lo pasa a `Auditor` como afectado; si toca varios (por ejemplo, la cuenta de un usuario con perfil en dos ámbitos), queda un registro por cada uno.
- Lo que se pueda garantizar en la base (unicidad, pertenencia a la misma entidad fiscal, una sola fábrica) va como restricción, no solo en el servicio.

### Seguridad

- Perfiles fijos por ámbito: `dueno_fabrica`, `dueno_local` y `empleado_local`, más el administrador técnico (`usuarios.es_admin_tecnico`), que no tiene ámbito ni ve datos comerciales.
- Los permisos se validan siempre en el servidor. El ámbito sale de la sesión, nunca de un parámetro que mande el front. Pedir por id un registro de otro ámbito devuelve 404.
- Login propio (`seguridad.LoginService`) con sesión en la base (Spring Session JDBC). La sesión guarda un `seguridad.Sesion` (usuario, ámbito activo, perfil). Spring Security solo aporta CSRF, encabezados y filtros; no usa `UserDetails` ni `@PreAuthorize`.
- Cada servicio valida el acceso al principio, con `seguridad.Acceso`: `exigirAdminTecnico()`, `exigirPerfil(...)` o `exigirAmbito()`.
- `seguridad.FiltroSesionVigente` verifica en cada pedido a `/api/**` que el usuario, su perfil y su ámbito sigan activos. Si no, cierra la sesión.
- CSRF: el front pide `GET /api/auth/csrf` (deja la cookie `XSRF-TOKEN`) y manda ese valor en el header `X-XSRF-TOKEN` en cada POST, PUT o DELETE.
- Para la API, 401 significa sin sesión y 403, sin permiso. Un login fallido responde siempre el mismo mensaje (`LoginService.LOGIN_FALLIDO`).

## Cómo levantar el entorno

```sh
cp .env.example .env               # completar POSTGRES_PASSWORD; .env no se sube al repo
docker compose up -d               # PostgreSQL 16 en localhost:5432
cd backend && ./mvnw spring-boot:run   # API y front en http://localhost:8080
```

La app lee el `.env` de la raíz (`spring.config.import`), así que no hace falta exportar variables. El `.env` se lee como ISO-8859-1: no usar tildes en sus valores.

Al arrancar, si no existe ningún administrador técnico, se crea uno con `ADMIN_EMAIL` y `ADMIN_PASSWORD` del `.env`.

## Tests

```sh
cd backend && ./mvnw test
```

- Necesitan Docker corriendo: los tests de integración levantan un PostgreSQL 16 propio con Testcontainers (`TestcontainersConfig`) y no usan la base de `docker compose`.
- Cada módulo cubre sus reglas de acceso con tests de integración: qué perfil puede hacer qué y que nadie vea datos de otro ámbito.
- Los tests de integración llevan `@PruebaIntegracion`: comparten un solo contexto y un solo contenedor, y cada test se revierte al terminar.
- `Datos` crea los datos de prueba. Con `datos.en(ambito, perfil)` y `datos.admin()` se obtiene un request con sesión real y token CSRF, sin pasar por el login. `Datos.login(...)` y `Datos.con(cookie)` hacen el login real por la API.
- Sacar `.with(csrf())` de un POST de prueba lo hace fallar con 403.

## Reglas de negocio

1. Un usuario puede tener un perfil en cada ámbito (la fábrica o un local). Por ejemplo, los dos dueños de la fábrica son también dueños del local central y entran con una sola cuenta.
2. El empleado de local ve otra interfaz y menos datos que el dueño. No ve costos, márgenes, cuenta corriente con la fábrica ni reportes financieros.
3. Cada pedido, venta, movimiento de stock, cierre de caja y comprobante pertenece a un ámbito. Nadie accede a datos de otro local. La fábrica no ve la caja interna de los locales.
4. El stock actual es la suma de los movimientos (venta, compra, producción, entrega, ajuste, conteo, devolución). No se edita directamente, y todo ajuste manual exige un motivo.
5. Pedidos online: se reserva el stock al confirmar, se descuenta al entregar o cobrar, y se libera si el pedido vence sin pago. El pago solo se habilita cuando el local confirma el pedido.
6. La entrega de la fábrica a un local es una venta, no una transferencia interna: tiene precio, comprobante y cuenta corriente entre ambos. El stock entra al local cuando este confirma la recepción.
7. Los saldos de cuentas corrientes se calculan siempre a partir de movimientos y nunca se editan a mano.
8. La fábrica y cada local son entidades fiscales independientes, con su CUIT, condición frente al IVA y puntos de venta. El tipo de comprobante depende de la condición del emisor y del receptor.
9. Se registra en auditoría, con usuario, perfil, ámbito, acción y fecha, toda operación sensible: confirmar o rechazar pedidos, ventas, anulaciones, cierres de caja, compras, producción y ajustes de stock.
10. Nunca se borran usuarios, productos, clientes ni proveedores: se desactivan para conservar el historial.

## Decisiones de usuarios y acceso

- Quién crea a quién: el administrador técnico crea los dueños de fábrica y de local. El dueño de local crea solo empleados de su local. El dueño de fábrica no crea usuarios.
- Solo el administrador técnico edita entidades fiscales. El dueño de local puede editar la dirección y los horarios de su local.
- Solo el administrador técnico crea ámbitos (fábrica y locales) y puntos de venta.
- El dueño de local edita de su local la dirección, los horarios, el teléfono y el email. El administrador técnico es el único que cambia el nombre del local y decide si se muestra en la web.
- Cada edición queda en auditoría con el valor anterior y el nuevo.
- La sesión vive en el servidor (no JWT). Bloqueo tras 5 intentos fallidos durante 15 minutos, sesión de 30 minutos sin actividad y contraseña de al menos 10 caracteres.
- Auditoría: cada dueño ve los registros cuyo ámbito actuante o afectado es el suyo, sin los eventos de login y sesión (`Auditor.ACCIONES_DE_ACCESO`). El administrador técnico ve todo y el empleado no ve nada.

## Forma de trabajo

- Se trabaja por etapas y, dentro de cada etapa, de a un módulo por vez. Orden de etapas: (1) base, usuarios, perfiles y auditoría; (2) catálogo, precios y stock; (3) clientes, pedidos, ventas, caja y cuenta corriente fábrica-local; (4) proveedores, compras y producción; (5) reportes; (6) facturación con ARCA.
- Antes de programar una etapa, presentar un plan y esperar aprobación. Después de cada módulo, resumir qué se hizo y qué tests pasan.
- Si algo no está definido en los documentos, preguntar en lugar de inventarlo.
- Identidad visual: verde institucional #00AE4C, verde profundo #1A312B, verde medio #29683D y gris #C3C3C3.
